# Decisions

Append-only. Newest at the bottom. Format: ID, date, decision, reason.

- **D-1 (2026-10-27)** Two orchestrators (private, work) instead of one generic personal agent. A generic agent had too little to do.
- **D-2 (2026-10-27)** One codebase, instances configured outside the repo. Enables two instances and a possible public release.
- **D-3 (2026-10-27)** Claude Agent SDK in TypeScript as the engine. Gives the `canUseTool` callback, structured output and cost per run in-process.
- **D-4 (2026-10-27)** Authentication via API key from a dedicated Console workspace per instance (spend limit = hard budget). Plan login stays a config option.
- **D-5 (2026-10-27)** Private instance on an always-on desktop machine, work instance on the work laptop. Physical separation of work data; the laptop's sleep is acceptable, watchers catch up.
- **D-6 (2026-10-27)** Orchestrator has only proposal tools; readers are tool-less; only the updater is a full agent. Reason: a compromised orchestrator can only propose.
- **D-7 (2026-10-27)** Rules change only via operator approval. Self-modifying rules are an injection path.
- **D-8 (2026-10-27)** No workflow engine. SQLite with state machines, idempotency keys and backups suffices for one user.
- **D-9 (2026-10-27)** No agent-to-agent protocol. A small HTTP mailbox on the always-on machine, reached over Tailscale; a shared SQLite file across machines risks corruption.
- **D-10 (2026-10-27)** Telegram as typing channel (official bot API, inline buttons, long polling, 24 h buffering). Signal rejected: no bot API, unofficial client with frequent protocol breaks, no buttons. Threema rejected: public callback required, messages dropped after three retries, groups provisional, paid per message. Built as a replaceable adapter.
- **D-11 (2026-10-27)** No custom chat or web UI.
- **D-12 (2026-10-27)** Pushover for alarms only.
- **D-13 (2026-10-27)** `proton-cli` for mail and calendar, read-only via wrapper, called by watcher code only.
- **D-14 (2026-10-27)** One fine-grained GitHub token (contents and pull requests, no admin/delete) instead of per-repository tokens. Repository allowlist enforced in code. Accepted risk: a bug could open a branch or PR in a non-listed repository.
- **D-15 (2026-10-27)** Existing server-health script is reused as a watcher via subprocess, unchanged.
- **D-16 (2026-10-27)** The orchestrator never modifies its own repository. New features come from operator-driven development sessions.
- **D-17 (2026-10-27)** Instance data lives outside the repo instead of being gitignored; secrets in the macOS Keychain. Pre-commit runs gitleaks plus a denylist kept outside the repo. Reason: the repo may become public, and history is published with it.
- **D-18 (2026-10-27)** Product name `ssstnt` ("assistant" without vowels), in the style of the operator's knowledge tool. Free on npm, GitHub and common domains at decision time. "Orchestrator" stays the name of the deciding role inside the system.
- **D-19 (2026-10-27)** Product name changed to `dsptchr` ("dispatcher" without vowels), superseding D-18; the triple "s" in `ssstnt` read badly. No project uses the name; free on npm, PyPI, crates.io and Homebrew at decision time. Docs site planned on a subdomain of the operator's site, npm package optional.
- **D-20 (2026-10-27)** No build step. Node 24 runs the TypeScript sources directly (type stripping); packages export `src/index.ts`. TypeScript runs only as type checker with `erasableSyntaxOnly`. Reason: fewer moving parts, no dist drift.
- **D-21 (2026-10-27)** SQLite via the built-in `node:sqlite` instead of a native addon. Reason: no dependency, no native build.
- **D-22 (2026-10-27)** Instance settings that are not sources or policy (timezone, channel IDs) live in `instance.yaml`. Secrets resolve lazily through `secrets.yaml` keychain references and are wrapped in a `Secret` type that never prints its value.
- **D-23 (2026-10-27)** Leak guard prints only the denylist entry number for a hit, never the term. Reason: CI logs may become public; the terms must not.
- **D-24 (2026-10-27)** The audit log is hash-chained and protected against UPDATE/DELETE by triggers. It records IDs, states, times and gate reasons, never todo or message text.
- **D-25 (2026-10-27)** Telegram offsets are confirmed on the next poll (at-least-once). Handlers use the channel event ID as idempotency key, so redelivery after a crash creates no duplicates.
- **D-26 (2026-10-27)** Kill switch: "stop" sends its confirmation first, then pauses. While paused the gate denies every action, including replies. "start" resumes, then confirms.
- **D-27 (2026-10-27)** Button presses are answered with a reply via `telegram.send`, not with a callback acknowledgement. An acknowledgement would be a new executor action (protected path). Repeated presses answer "Already done".
- **D-28 (2026-10-27)** Until the reader model exists, due dates come from a deterministic parser with an explicit ` @ ` separator (`in 2h`, `18:00`, `morgen 9:00`, `2.11. 14:00`). Unreadable dates are refused, never guessed.
- **D-29 (2026-10-27)** Until operator approvals exist (Phase 2), the daemon refuses to start with any `ask` level in the policy. An `ask` action would otherwise wait forever.
- **D-30 (2026-10-27)** A recovered `approved` action (crash between gate and executor) runs only if the kill switch is off and the current policy still says `auto`. Stranded `proposed` actions go through the gate again.
- **D-31 (2026-10-27)** Executor action types are messenger-neutral: `message.send` and `message.ack` replace `telegram.send` (AR-8). Supersedes the naming in D-27.
- **D-32 (2026-10-27)** Button presses are answered with `message.ack` (short note, buttons removed), superseding D-27. Approved by the operator.
- **D-33 (2026-10-27)** Local executor actions commit their store changes and the action's success in one transaction. Remote actions are at-least-once: a crash after the effect repeats it.
- **D-34 (2026-10-27)** Durable inbox for operator input. The daemon stores received events in SQLite before the channel confirms them, then processes them from there. Failed events retry with growing delays (1 min doubling, at most 1 h) and are set aside as `dead` after 5 attempts; the operator gets a message. Payloads of handled events are dropped after 7 days; the ID stays for dedupe. Supersedes the audit-only gap noted for D-25.
- **D-35 (2026-10-27)** A failed action makes the operator handler throw, so the inbox retries the event; the dispatcher retries a failed action under the same idempotency key if pause state and policy allow it. Dead-event notifications are tracked in the store and retried until delivered. Telegram requests time out (15 s, plus the poll time for long polls); the inbox drains in the background so a slow handler never blocks receiving or the scheduler.
- **D-36 (2026-10-27)** Inbox handlers time out after 60 s; the attempt counts as failed and the drain moves on, so "stop" is never stuck behind a hanging event. Dead-event notices use one idempotency key per hour, so a denial (for example by the rate limit) is retried later.
- **D-37 (2026-10-27)** No Pushover. Alarms go through Telegram like all other messages; supersedes D-12. Accepted trade-off: Telegram does not break through "Do Not Disturb" the way Pushover emergency priority does.
- **D-38 (2026-10-27)** No Shortcut HTTP endpoint in Phase 1. Telegram covers quick capture; the endpoint would add an open port for Siri-only convenience.
- **D-39 (2026-10-27)** The heartbeat to the external push monitor is deterministic daemon code outside gate and executor, a documented exception to AR-4. It carries no content (status and "ok"/"paused" only) and must keep running while the kill switch is active, otherwise the monitor would alarm on every pause. The push URL is a secret.
- **D-40 (2026-10-27)** The server health watcher runs the existing script with `run --dry`, so the script's own state and schedule stay untouched; dsptchr deduplicates in its `observations` table. Until readers exist, alerts are deterministic: new, escalated and resolved warn/crit findings go in one message to the operator's own conversation. Finding text comes from the servers, so it is sanitized (no control or bidi characters, one line, bounded length) and never reaches a model or any other recipient. Changes are recorded only after the message went out. Three failed checks in a row raise one alert.
- **D-41 (2026-10-27)** `server_health.hosts` is a required allowlist. The existing check script covers the hosts of more than one instance; findings of hosts outside the list are dropped before they are stored or sent, so work data never reaches the private instance and vice versa.
- **D-42 (2026-10-27)** The orchestrator runs on the Messages API (`@anthropic-ai/sdk`) with a manual tool loop instead of the Agent SDK; supersedes D-3 for orchestrator and readers. Reason: the Messages API has no built-in shell, file or network tools to disable and loads no settings or hooks from the working directory, so AR-1 holds by construction. The Agent SDK stays the plan for the sandboxed updater (Phase 2). Dependency: `@anthropic-ai/sdk`, the official client.
- **D-43 (2026-10-27)** Operator free text goes to the orchestrator (default `claude-sonnet-5-5`, effort `low`). Its tools: `read_state` (todos, health, status), `create_todo`, `update_todo`; each write is a proposal through gate and executor, keyed by event ID and input hash so retries do not duplicate. It sees operator text, its own last replies (6 h, at most 12 turns) and structured state; health finding text never enters its context. The kill switch and `/` commands never touch the model. A daily budget (`orchestrator.daily_budget_usd`) stops model calls for the day; on budget stop or API failure the message falls back to the deterministic todo path with a note. Server-side refusal fallback is enabled (`fallbacks: "default"`).
- **D-44 (2026-10-27)** Orchestrator hardening after review. Health findings reach the model only as host, severity, scope (host/container) and a rule name matching `[a-z_]`; server-supplied identifiers never do. Per event the store keeps completed writes and the final reply: a retry resends the stored reply, or tells the model what is already done. If the model fails after a write, the operator gets a summary instead of a fallback todo. Spend is recorded per API response, and the budget is checked before every call. `/todos` and `/health` cap their output to one message.
- **D-45 (2026-10-27)** GitHub watcher, observe level, read-only token. Every 15 minutes per configured repository: open PRs, open issues and the latest completed run per workflow on the default branch. Immediate alerts only for new PRs and issues by others, CI turning red and CI recovering; own and bot items (Dependabot, Renovate) appear in the morning briefing and `/github`. Titles are untrusted: sanitized, sent only to the operator, never to a model; the orchestrator sees per-repository counts only. Observations are keyed by the configured repository name, not the API response.
- **D-46 (2026-10-27)** GitHub watcher refinements after the first live run and review. The first successful sync of a repository is a silent baseline. Only active workflows from `.github/workflows/` count as CI (GitHub's dynamic Dependabot and code-scanning workflows do not), named by the workflow, not the run title. "Green again" needs a successful run; cancelled or skipped runs change nothing. Lists are paginated (up to 10 pages); an incomplete snapshot resolves nothing. Failure streaks are tracked per repository. Telegram link previews are off for all bot messages.
- **D-47 (2026-10-27)** Injection suite: deterministic scenarios in `pnpm test`, live model scenarios in `pnpm test:injection`. The suite found that one message could make a misbehaving model create unlimited todos; one operator message may now cause at most 10 changes.
- **D-48 (2026-10-27)** Proton access uses the operator's own account, not a bot account (operator decision; Proton Pass is unused). Accepted risk: the proton-cli session also reaches Drive and account settings. Mitigations: only watcher code calls the CLI, through a wrapper that allows `mail messages list|get` and `calendar events list` with validated arguments; `PROTON_CONFIRM=mutations=deny`, no update check, no CLI log, minimal environment. The binary is pinned to v5.1.0 (sha256 `3ceda229c11ee3a301bca0e16852bdf90f8a7250a4c5046df4d8391fbf2176c4`, darwin/arm64), verified against the release checksums and the GitHub API digest, installed outside `PATH`.
- **D-49 (2026-10-27)** Calendar via proton-cli every 30 minutes, today and tomorrow, stored as observations. Briefing, `/calendar` and the orchestrator read from the store. Titles of events organized by others (invitations) are untrusted: the operator sees them sanitized, the model sees "(invitation)".
- **D-50 (2026-10-27)** Mail via proton-cli every 15 minutes, inbox only, starting from the first run (no backlog). Each new mail goes to the reader (`claude-haiku-5-5`, one tool-less call, JSON schema output, mail wrapped as untrusted data); its cost counts toward the daily model budget, beyond which mail is stored unclassified. Urgent personal or important mail alerts immediately; the morning briefing lists mail worth reading from the last 24 h; `/mail` shows details. Sender, subject and summary are sanitized and reach only the operator; the orchestrator sees counts. Todo mail: mail to `todo_address` from one of `own_addresses` becomes a todo (subject, optional ` @ due`); from anyone else it is ordinary mail. Accepted risk: a spoofed own address can create a todo.
- **D-51 (2026-10-27)** Mail and calendar hardening after review. Mail listings are paginated; the mail cursor advances only when the listing was complete, every mail was recorded and every urgent alert went out. A todo mail whose todo could not be created stays unprocessed. Todos created from mail show as "(todo from mail)" to the model, because a spoofed own address could control their text. Calendar events count as own only when the organizer is known to be empty or an own address.
- **D-52 (2026-10-27)** iCloud calendar over CalDAV and birthdays over CardDAV with an app-specific password, read-only by construction (only PROPFIND and REPORT are ever sent). iCloud has no birthday calendar over CalDAV, so birthdays come from contact `BDAY` fields. Events merge with Proton events in the calendar view; recurrences expand with `ical.js`, WebDAV XML parses with `@xmldom/xmldom` (both without dependencies). Writing to iCloud would be a new executor action.
- **D-53 (2026-10-27)** Receipts from code: every orchestrator reply ends with the changes that really happened ("✓ Created todo …"), taken from the per-event write record, not from the model. A reply that sounds like a change without one gets "(No change was made.)". The receipts also land in the chat memory, so the model sees reliable history. Prompt rules: changes only through a tool call in the current turn; earlier mistakes are reported and asked about, never repaired unasked. Default effort is `medium` (at `low` the model inferred history wrongly and acted on it). The model can look up all birthdays (`read_state birthdays`).
- **D-54 (2026-10-27)** The calendar watcher keeps 90 days back and 60 days ahead in the store (Proton paginated, iCloud expanded), so the orchestrator can answer "when was I at …" with the new read-only tool `search_calendar` (query, date range, at most 50 results). Queries match only own event titles; invitations from others show as "(invitation)" in plain listings.
- **D-55 (2026-10-27)** iCloud and mail hardening after review. iCloud credentials go only to `(pNN-)caldav|contacts.icloud.com` over HTTPS; every server-supplied URL is checked, redirects are errors. Recurrences step from DTSTART (up to 20,000 steps), moved exceptions count by their own dates and organizer, event keys include the calendar, floating times keep seconds. Mail: a denied todo creation retries under a new attempt key; a listing cut short by the page limit no longer blocks the cursor, the operator is told once that older mail was skipped. Mail-derived todo text stays hidden from the model in update results and receipts too.
- **D-56 (2026-10-27)** Full use of the operator's knowledge base through its CLI (Markdown notes in Git), so there is one knowledge store, not two (operator decision). The orchestrator reads with `search_knowledge` and `read_knowledge` and changes notes with `write_knowledge` (create, append, replace with revision check), which becomes the executor action `knowledge.write` (auto, at most 20 per hour). The CLI enforces scope (`privat` for this instance) and locks sensitive paths; the code never releases them. Every write is a local commit in the knowledge base, so changes are visible and reversible; dsptchr never runs the CLI's sync. Accepted risk: saved web pages in the knowledge base can carry injected text into model context; rate limit, receipts and git history bound the damage. Approved by the operator in this session (protected path).
- **D-57 (2026-10-27)** The knowledge integration is a generic adapter contract (`docs/knowledge.md`); supersedes the CLI wrapper of D-56. The operator's concrete adapter lives in the instance directory and is loaded at start, so the repository carries no knowledge-tool specifics. Gating, rate limit and receipts stay as in D-56.
- **D-58 (2026-10-27)** Review fixes: iCloud exceptions with `RANGE=THISANDFUTURE` shift and rename every later occurrence; the mail backlog notice stays pending until delivered, once per backlog; `knowledge.write` keeps commit messages within 120 characters.
